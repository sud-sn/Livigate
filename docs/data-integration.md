# Connecting a client's data

How Levigate reads a pharmacy's Snowflake warehouse, how a client's own tables are mapped, how logic that already
lives in the client's BI is reused, and how we prove the result is right before anyone works from it.

## 1. What Levigate reads, and how

* **Read-only, always.** Levigate connects with a read-only Snowflake role. The connector only runs *named queries*
  registered in code (`backend/levigate/connectors.py`) with typed, bound parameters. Nothing is created, written or
  cached in the client's warehouse, and no free-form SQL from users or the AI ever reaches it.
* **Seven canonical relations.** Every query and rule is written once, against these relations:

| Relation | One row per | Columns |
| --- | --- | --- |
| `FACT_RXFILL` | dispensed (or attempted) fill | `FILL_ID, RX_NUMBER, FILL_NUMBER, PATIENT_ID, PRESCRIBER_ID, DRUG_ID, PAYER_ID, LOCATION, FILL_DATE, DAYS_SUPPLY, QUANTITY, REFILLS_AUTHORIZED, REFILLS_REMAINING, RX_WRITTEN_DATE, RX_EXPIRES_DATE, STATUS, PICKUP_READY_DATE, PATIENT_BALANCE, EXPECTED_AMOUNT` |
| `FACT_CLAIM` | claim submission or reversal (primary payer) | `CLAIM_ID, FILL_ID, RX_NUMBER, FILL_NUMBER, PAYER_ID, SUBMITTED_AT, RESPONSE_STATUS, REJECT_CODE, REJECT_MESSAGE, BILLED_AMOUNT, EXPECTED_AMOUNT, PAID_AMOUNT, ADJUDICATED_AT, REMITTED_AT, UPDATED_AT` |
| `DIM_PATIENT` | patient | `PATIENT_ID, FIRST_NAME, LAST_NAME, DOB, PHONE, ZIP, PREFERRED_LANGUAGE` |
| `DIM_PRESCRIBER` | prescriber | `PRESCRIBER_ID, NPI, FIRST_NAME, LAST_NAME, CREDENTIAL, SPECIALTY, PRACTICE_NAME, PHONE, FAX, EMAIL, CITY, STATE` |
| `DIM_PAYER` | payer | `PAYER_ID, PAYER_NAME, BIN, PCN, PLAN_TYPE` |
| `DIM_DRUG` | drug or compound formula | `DRUG_ID, DRUG_NAME, FORM, IS_COMPOUND, UNIT_PRICE` |
| `PATIENT_CONSENT` | consent change per channel | `PATIENT_ID, CHANNEL, STATUS, CONSENT_TYPE, RECORDED_AT, UPDATED_AT` |

* **Fixed vocabularies** (`VOCABULARY` in `backend/levigate/sources/base.py`): fill `STATUS` is `picked_up`,
  `ready_for_pickup` or `on_hold`; claim `RESPONSE_STATUS` is `P` (paid: a remittance exists), `C` (captured,
  payable, no payment yet), `R` (rejected), `X` (reversed); `PLAN_TYPE` is `Commercial`, `Medicare Part D`,
  `Medicaid`, `Workers' comp`, `Cash` or `Other`; consent `CHANNEL` is `call` or `sms`, `STATUS` is `granted` or
  `revoked`. The mapping translates the client's codes into these; a data check fails on any value outside them.
* **The change marker.** `FACT_CLAIM.UPDATED_AT` and `PATIENT_CONSENT.UPDATED_AT` must be the time the row *landed in
  the warehouse* (for a Talend pipeline, `LOAD_TS`), not the business event time. The 15-minute sync reads rows
  changed since its watermark with a 30-minute overlap, so a row that lands late is never skipped. The first sync of
  each business day re-reads everything (claim status also depends on the date), and an admin can request a full
  re-read at any time (Admin → Sync and health → Full re-read).

## 2. Two ways to onboard a client

**A. The client publishes seven views.** Their data team creates views with exactly the names and columns above;
Levigate uses the `canonical` profile and reads them directly. Simplest, and the client keeps ownership of the logic.

**B. Levigate maps their tables.** We write a *source profile*: a Python module in `backend/levigate/sources/` that
defines each canonical relation as a `SELECT` over the client's own tables. At query time the connector puts only the
definitions a query needs in front of it as `WITH` clauses — still one read-only statement, nothing stored in their
warehouse. Profiles are code: reviewed in a pull request, versioned, never edited from the UI and never generated by
a model. The admin screen (Admin → Data source) shows the mapping SQL read-only.

`pms_snowflake.py` is the worked template: a pharmacy system's normalised tables as Talend lands them —
`PATIENT`, `PATIENT_PHONE`, `PATIENT_COMM_PREF`, `PRESCRIBER`, `PRESCRIBER_ADDRESS`, `PAYER`, `PLAN`,
`PLAN_CONTRACT`, `PATIENT_INSURANCE`, `STORE`, `FORMULA`, `FORMULA_INGREDIENT`, `RX`, `RX_FILL`, `CLAIM_TXN`,
`CLAIM_REJECT`, `REJECT_CODE_REF`, `REMIT_835` — plus two BI views. Every judgment call sits next to its SQL:

| Real-world situation | What the mapping does |
| --- | --- |
| Talend reloads land the same fill twice | Latest `LOAD_TS` per `FILL_KEY` wins (`SRC_FILL`) |
| Fills entered in error and voided | Soft-deleted rows (`IS_DELETED = 'Y'`) excluded |
| A rejection carries up to five reject codes | Routed on the first (`REJECT_SEQ = 1`); others stay in the source |
| Secondary-payer (COB) claims | Only claims to the plan billed on the fill (pilot scope) |
| "Paid" means money arrived | Payable response + an 835 line = Paid; without one = Captured |
| Payer splits a payment across 835s | Amounts summed; the last payment date is the remittance date |
| Claim lands before its fill row | Not mapped until the fill arrives; counted by a data check |
| Contract terms change over time | The contract in force on the fill date is used |
| Payer response time | `CLAIM_TXN.RESPONSE_TS` → `ADJUDICATED_AT` |
| Plan types stored as codes (`COMM`, `MCR_D`, …) | Translated to the vocabulary |
| Names in capitals, phones in five formats | Normalised once in the service layer (`services.normalize_patient`) |
| E-mail preferences in the consent table | Ignored (call and text only in the pilot) |

Writing a new profile:

1. Copy `pms_snowflake.py`; define each relation (and shared `SRC_`/`BI_` helpers) over the client's tables;
   list `source_tables` for every relation; add raw-table `quality_checks` for the client's known mess.
2. Register it in `sources/__init__.py`.
3. Point a test environment at a copy of the client's schema (or a synthetic layout that mirrors it) and run the
   checks in §4. Merge only when all pass.

## 3. Reusing logic the client's BI already has

Pharmacies usually have business logic in BI views already — expected reimbursement, "unpaid", prescriber volume.
A profile can reuse it in either of two ways, and the demo ships both so they can be compared:

* **Port the formula** (`pms_snowflake`): the BI's expected reimbursement — the lesser of U&C and
  AWP × quantity × contract rate + dispensing fee, using the contract in force on the fill date — is written into
  the mapping. Levigate owns the formula; it is reviewed and tested like the rest of the code.
* **Bind to the BI view** (`pms_snowflake_bi`): `EXPECTED_AMOUNT` is read straight from the client's
  `VW_CLAIM_STATUS.EXPECTED_REIMB`. The client keeps a single source of truth; if their BI team changes the
  formula, Levigate follows automatically.

Either way, the **BI comparison** (Admin → Data source → Compare) checks Levigate against the client's BI views fill
by fill: expected reimbursement, claim status, days to payment and prescriber volume. Differences are grouped and
each group is marked *explained* when it comes from a definition that differs on purpose, for example:

* the BI marks a claim unpaid after a flat 30 days; Levigate uses each payer's own window from the business catalog;
* the BI has no "underpaid" status; Levigate flags payments below the expected amount by more than the threshold;
* the BI counts only fills the patient picked up as prescriber volume; Levigate counts every fill.

Anything unexplained points at a mapping error or bad data, and is listed with sample Rx numbers (never patient
details). Logic that should *not* be shared — status windows, routing, thresholds — lives in the business catalog,
where changes need a second admin's approval and are versioned.

## 4. How a mapping is proven correct

| Check | Where | What it proves |
| --- | --- | --- |
| Column contract | Admin → Data source; `test_sources.py` | Every relation returns exactly the canonical columns |
| Snowflake dialect | `test_sources.py` | Every query, check and mapping, composed exactly as sent, parses as Snowflake SQL, uses only functions Snowflake has, and contains no writes |
| Same answers on every layout | `test_sources.py` | All 25 shared named queries return identical business rows from the reference tables and from both client mappings (the 2 BI queries agree between the two client variants) |
| Every role sees the same | `test_layouts.py` | Full environments on three layouts: identical work items and identical API answers for all 7 roles |
| Incremental sync misses nothing | `test_layouts.py` | After today's load lands and the 15-minute sync runs, a full re-read changes nothing |
| Data checks find the mess | `test_sources.py`, `test_data_source.py` | Each injected problem (reload duplicates, voids, COB, split 835s, …) is counted exactly |
| Wrong mappings are caught | `test_sources.py` | Mutations — keeping duplicates, ignoring contract dates, dropping the U&C rule, a missing column, untranslated codes — each fail a check |
| BI parity | `test_data_source.py`, Admin → Data source | Expected amounts and payment dates agree to the cent and day; every status and volume difference is explained |

**Data checks** run with every sync and on demand (shared checks on the canonical relations plus the profile's own
raw-table checks). Each reports a count and an explanation, never patient details: missing fill dates or days
supply, duplicate fills after mapping, claims without a fill, rejections without a code, paid claims without a
remittance date, missing expected amounts, future-dated fills, unknown patients/prescribers/payers, patients without
a phone (kept off call lists until a number is added), consent for unknown patients, and values outside the
vocabularies. A failing check never stops work items from being built; it shows on the sync step and the admin screen.

## 5. Onboarding checklist

1. Client creates a read-only Snowflake role and a key-pair user; the secret goes in the vault, the connection stores
   only its reference (Admin → Data connections).
2. Choose route A (seven views) or B (source profile). For B, get the table list, keys and the change-marker column.
3. List the client's BI views and the definitions they encode; decide per definition: port, bind or catalog.
4. Run the column contract, the data checks and the BI comparison against the client's warehouse. Resolve every
   failing check and every unexplained difference with the client's data team.
5. Load the business catalog (payer windows, reject-code playbook, refill thresholds) and have a second admin approve.
6. Turn the scheduled sync on; watch the first business day's full scan and the incremental runs after it.
